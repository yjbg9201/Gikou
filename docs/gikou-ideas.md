## 0. 目的と使い方

本書は、2026年7月〜8月のチャットで蓄積した技巧（Gikou 2）改造アイデア5件と既存仕様書4本を一本化し、Claude Code の cloud session に1タスクずつ発注するための親仕様書である。

- **対象リポジトリ**: Gikou-master を GitHub に fork（またはミラー）したもの。cloud session は GitHub 連携リポジトリ上で動くため、ローカルの zip 運用から移行する。
- **置き場所**: 本書を Markdown で書き出し `docs/gikou-ideas.md` に置く。既存仕様書の原本（§1）も `docs/specs/` に置き、`CLAUDE.md` から参照させる。
- **発注の書式**: 「`docs/gikou-ideas.md` の G2 フェーズ1を実装。受け入れ基準を満たすまで進めて PR を作成」のように ID と範囲で指示する。
- **ライセンス**: 技巧・やねうら王とも GPL-3.0。移植コードには出典コメントと原著作権表示を残す。

ID の意味: **G** = 技巧本体の改造、**T** = 技巧を土台にした外部ツール、**R** = 関連（他エンジン側の改造、参考のみ）。

## 2. 技巧の構造に関する確定事項

技巧の評価関数は NNUE ではなく、4チャンネルのスパース線形評価に固定の非線形合成ヘッドを載せた構造である。以下は過去のソース解析で確定した事実で、全タスク共通の前提として扱う。

- **実行時に必要な評価ファイルは `params.bin` のみ**（259,336,912 bytes、`EvalParameters` の生ダンプ、12テーブル）。進行度は KP テーブルの第4スロット（`PackedScore[3]`）に、駒割りは KP に焼き込み済み。`probability.bin` は探索（実現確率）専用。
- **評価項目**: KP・PP・controls（マスごとの利き数）・king\_safety・飛び駒・tempo の6成分。1局面のアクティブ特徴は最大約1,100〜1,200。
- **PackedScore の符号規約は2系統**: 3x1系（KP・tempo: 序盤/中盤/終盤＋進行度重み）と 2x2系（その他: 序盤/手番/終盤/手番）。先後反転で符号が変わらないチャンネルが異なる。
- **進行度** p = σ(KP第4チャンネル総和 / 2^16)。`progress.bin`（683,640 bytes）から KP スロット3へ転記される。
- **PP 対称性** `T[a][b] = T[b][a]` は差分評価の整合性を支えるハード不変条件。
- **学習**: 主損失は棋譜指し手との比較学習（`kifu_db.txt` 必須）、補助損失は RootStrap と勝敗ロジスティック回帰。勝率換算は sigmoid(v/600)、学習時に歩=100 で固定。バッチ 80,000 の復元抽出。
- **座標・駒番号**: 技巧 PieceType は 金5・角6・飛7、やねうら王は 角5・飛6・金7。手駒の列挙順も技巧は歩香桂銀**金角飛**。
- **SFEN**: `Position::ToSfen()` は手数を常に `  1 ` で出力する（実手数を持たない）。
- **評価値の視点**: 技巧の定跡は先手視点、やねうら王の定跡・PSV は手番視点。
- **ビルド**: `make release`、`-std=c++11 -msse4.2 -fopenmp`。g++ 13.3 で警告なしビルドを確認済み。`MINIMUM` ビルド設定が存在する。

### G0. リポジトリ化とビルド基盤

cloud session 運用の前提として、技巧原本を GitHub リポジトリ化し、以降の改造を PR 単位で積む。

- 原本を初回コミットとしてタグ付け（`upstream-original`）。以降の比較・パッチ再生成の基準にする。
- `CLAUDE.md` に、ビルド手順、本書と `docs/specs/` の場所、§4 の落とし穴、「既存挙動を変えない（後方互換）」原則を書く。
- GitHub Actions で `make release` と各タスクのセルフテストを回す。評価ファイル（約248 MiB）はリポジトリに入れず、テストはランダム生成 params.bin で行う（G3 の検証方式を流用）。
- **受け入れ基準**: クリーン環境で `make release` が警告追加なしで通る。

### G1. やねうら王 PSV 教師による学習（実装済み）

技巧の強化学習段（RootStrap・勝敗回帰の補助損失）の教師を、やねうら王 PackedSfenValue（40 bytes/レコード）から直接読めるようにする。主損失（棋譜比較学習）には手を入れない。

- **追加 CLI**: `--learn-psv`、`--learn-psv-rootstrap`、`--convert-psv`、`--psv-selftest`。オプションは `scale=`、`eval_limit=`、`max=`。
- **新規ファイル**: `src/yaneuraou_psv.h/.cc`。変更は `cli.cc`・`learning.cc`・`learning.h` の3ファイル。
- **変換規則**: score・game\_result とも手番視点で符号反転不要。RootStrap 用は eval\_limit を適用し引き分けを残す。回帰用は引き分けを除外し eval\_limit を適用しない（技巧原仕様どおり）。駒箱に駒がある局面はスキップ。
- **scale**: 既定 1.0（両エンジンとも sigmoid(v/600) を共有）。駒割基準で合わせるなら 1.11（技巧 歩=100、やねうら王 PawnValue=90）。
- **付随修正**: 教師局面が 80,000 未満だと原コードが未定義動作になるため、明示エラーで終了するガードを追加済み。
- **取り込み作業**: パッチを G0 のリポジトリに適用し、`PSV_LEARNING.md` を `docs/` に置く。CI に `--psv-selftest` を追加。
- **受け入れ基準**: パッチ適用後のツリーが検証済みツリーとバイト一致し、セルフテストと Python 独立実装（3局面）のバイト一致が CI で再現する。

### G2. やねうら王定跡の読込（新規実装の本命）

技巧の `BookFile` にやねうら王形式の定跡を指定でき、ヒット時は探索せず定跡手を返す。既存の技巧形式 `book.bin` の挙動は一切変えない。

**フェーズ1（.db テキスト形式・全読込）**

- ファイル形式の自動判別: 先頭16バイトが `YANE-BINBOOK-V1\0` → .ybb、先頭行が `#YANEURAOU-DB2016` → .db、拡張子 .db → .db、それ以外 → 技巧形式。
- 新規 `src/yaneura_book.h/.cc`（`YaneuraOuBook` / `YaneBookMove`）。`thinking.cc` の定跡参照箇所で読込済みの形式に分岐。`OwnBook` や `BookMaxPly` などの呼び出し条件は変更しない。
- **キー正規化**: SFEN 末尾の手数を無視して照合（IgnoreBookPly 相当を常時有効。技巧の ToSfen が手数を持たないため必須）。
- **FlippedBook**: ミス時に先後反転局面で再照合し、指し手・評価値を反転して返す。既定で有効（ペタショック定跡は先手局面のみ格納の場合があるため）。
- **指し手選択**: やねうら王 `BookMoveSelector::probe_impl` を移植。BookIgnoreRate → 合法性フィルタ → BookDepthLimit → BookEvalDiff / BookEval{Black,White}Limit → 抽選。非合法手は除外し `info string` で通知。
- **評価値の視点変換**: やねうら王は手番視点、技巧は先手視点。既存の符号反転コードを流用しない。
- **USI オプション**: 既存の `BookFile`・`OwnBook`・`NarrowBook` を流用。`BookMaxPly` の上限を 50 → 10000 に拡張。新規は `BookIgnoreRate`(0)、`BookEvalDiff`(30)、`BookEvalBlackLimit`(0)、`BookEvalWhiteLimit`(-140)、`BookDepthLimit`(16)、`ConsiderBookMoveCount`(false)、`FlippedBook`(true)。depth 情報を持たない定跡では BookDepthLimit を自動無視する救済を入れてよい。
- **出力**: ヒット時に候補手を `info ... multipv ... score cp ... pv ...` で出力。破損時はエンジンを落とさず定跡なしで継続。
- **非機能**: 100万局面規模で読込数十秒以内、照合1回 1ms 未満、`MINIMUM` ビルドでもコンパイル可能。

**フェーズ2（.ybb バイナリ・巨大定跡）**

- 新規 `src/yaneura_book_ybb.cc` と、やねうら王互換 PackedSfen エンコーダ `src/sfen_packer.cc/.h`（encode のみ）。
- 照合は「現局面→PackedSfen 32B → 索引（32 + 44×i）を memcmp で二分探索」。全読込と `BookOnTheFly`（ディスク上二分探索）の2モード。
- Move16 → 技巧 Move は USI 文字列経由（`Move::FromSfen`）で座標・駒番号差を吸収。
- .ybb には採択回数がないため常に評価値ベースで選択。.db 指定で実在せず同名 .ybb がある場合は読み替える。
- **前提確認**: 技巧の `huffman_code.cc` がやねうら王 PackedSfen とビット一致するか。G1 の作業で `EncodePosition()` のバイト一致は3局面で確認済みのため、流用できる見込みが高い。CI で cshogi `to_psfen()` との比較テストを置く。

**受け入れ基準**: 原本仕様書の12項目テスト計画。最低限、(1) 既存 book.bin の回帰なし、(2) 平手・後手番・FlippedBook ヒット・非合法手混入の各局面で期待どおりの手と評価値符号、(3) 破損ファイルで起動継続。

### G3. 評価値ダンプ・ランダム局面生成（実装済み）

技巧に `--evaldump`（局面ごとの評価値・進行度・項目別内訳を出力）と `--randsfen`（ランダム自己対局局面の生成）を追加する検証用パッチ。R1 の整数完全一致検証で使った。

- T1 の M1（C++ 特徴量ダンパ）と順伝播一致テストの正解値ジェネレータとしてそのまま使える。
- **取り込み作業**: パッチ適用、CI でランダム params.bin を生成して `--evaldump` が完走することを確認。

### T1. params.bin の GPU トレーナー（外部ツール）

技巧の params.bin を読み、PSV（主）/ hcpe（副）教師で GPU 学習し、params.bin に書き戻す。技巧本体とは別リポジトリまたは `tools/trainer/` に置く。

- **推奨構成（Route A）**: PyTorch ＋ 技巧ソースを流用した C++ 特徴量ダンパ。合成ヘッドは autograd に任せる。代替は BulletOu 拡張（Route B）。
- **損失**: q = S\_stm/600 に対し、評価値教師と勝敗教師の λ 混合交差エントロピー（nnue-pytorch 方式）。L1 正則化、テーブル単位の凍結フラグ。
- **進行度**: 既定は凍結（KP スロット3 を読むが学習しない）。
- **工程**: M0 入出力 → M1 C++ ダンパ → M2 ローダ → M3 モデル → M4 学習ループ → M5 書き出し → M6 実験。
- **受け入れ基準**: round-trip でバイト同一、10,000局面で順伝播がエンジンと ±4 点以内、1,000局面の過学習で loss がほぼ 0。
- G1 とは役割が重なる（どちらも PSV 蒸留）。G1 は技巧の学習器のまま CPU で回す、T1 は GPU で高速に回す、という使い分け。

### R1. やねうら王上での技巧評価関数（参考）

やねうら王に `YANEURAOU_ENGINE_GIKOU` エディションを追加し、技巧の params.bin を最新探索部で動かす。技巧リポジトリの対象外だが、G3 と検証資産を共有する。Phase 1（全計算）は308局面で整数完全一致を確認済み。Phase 2（KP/PP/controls の差分計算）は未着手で、実用的な棋力比較は Phase 2 後になる。

## 4. 共通規約と落とし穴チェックリスト

過去の実装で実際にバグや取り違えが出た箇所を挙げる。各タスクの発注プロンプトに該当項目を明記し、CLAUDE.md にも転記する。

- [ ] **金・角・飛の PieceType 番号差**（技巧 5/6/7 = 金角飛、やねうら王 5/6/7 = 角飛金）。打ち駒の Move16 変換、手駒、controls、HandSet のすべてに効く。
- [ ] **手駒の列挙順**は技巧 PieceType 昇順（歩香桂銀金角飛）。PP が非対称のため順序違いで評価値が±1ずれる（R1 で検出）。
- [ ] **評価値の視点**: 技巧定跡は先手視点、やねうら王定跡と PSV は手番視点。PSV→技巧学習では反転不要、定跡では反転が必要。
- [ ] **SFEN の手数**: 技巧 ToSfen は常に `  1 `。手数を含むキーで照合しない。
- [ ] **PackedSfen のビット一致**: ハフマン符号表は一致確認済み。ビット順・手番/玉位置の配置・成り/先後フラグ位置・手駒順は実測テストで固定する。
- [ ] **ハフマン形式の3系統**: 技巧・Apery・やねうら王で成り/先後フラグの順序が異なる。技巧と Apery は「後手が金以外の手駒を持つ局面」でのみ食い違うため、平手や先手のみ手駒のテストは誤って通る。
- [ ] **不正 SFEN**: 駒数超過の局面を受理すると固定長リストが溢れる。駒種ごとの最大枚数でクランプする。
- [ ] **PackedScore 符号規約**: 3x1系（KP・tempo）と 2x2系（その他）を混同しない。
- [ ] **PP 対称性**: 書き出し時に対称化と検証を省略しない。違反しても即クラッシュせず差分評価が静かに壊れる。
- [ ] **80,000 局面ガード**: 学習ループの復元抽出はバッチ 80,000 未満で未定義動作。
- [ ] **後方互換**: 既存の book.bin、teacher\_positions.bin / teacher\_games.bin 経路、USI オプション既定値の挙動を変えない。
- [ ] **検証は独立実装と照合**: 実装同士の突き合わせではなく、やねうら王原典の Python 転写や cshogi など別実装との一致で確認する（G1・R1 で有効だった方式）。

## 5. 推奨実装順と cloud session への発注単位

小さな取り込み作業で cloud session の運用（PR・CI・レビュー）を固めてから、G2 の新規実装に進む順を推奨する。1セッション1タスク、各タスクの完了条件は §3 の受け入れ基準とする。

1. **G0** リポジトリ化・CLAUDE.md・CI（`make release`）
2. **G3** 検証用 CLI パッチの取り込み（以降のテストの正解値源になる）
3. **G1** PSV 学習パッチの取り込み、`--psv-selftest` を CI に追加
4. **G2-a** 形式判別と .db パーサ、キー正規化（照合まで。選択は先頭手固定）
5. **G2-b** 指し手選択ロジック移植、USI オプション追加、info 出力
6. **G2-c** FlippedBook と評価値の視点変換、破損時の継続動作
7. **G2-d** PackedSfen 互換性テスト（cshogi 比較）→ .ybb 全読込
8. **G2-e** BookOnTheFly と .db→.ybb フォールバック
9. **T1** は別リポジトリで M0 から並行可能（G3 完了後が望ましい）

発注時に渡すもの: 本書の該当節、§4 の該当項目、原本仕様書（G2 なら `gikou_yaneuraou_book_spec.md`）、参照すべきやねうら王ソースのパス（`source/book/book.cpp`、`sfen_packer.cpp`）。やねうら王ソースは別リポジトリとして cloud session に追加するか、`third_party/` に参照用として置く。
